# Salvor Connector 2.0.12

Fixes from a customer test on 2026-11-19. Upgrade on every branch (`16.0` to `20.0`).

## What changed
- **Behind Cloudflare:** when the address Odoo resolved for a request (the socket peer, or the
  right-most `X-Forwarded-For` entry with `proxy_mode`) is one of Cloudflare's published edge ranges,
  the allowlist checks `CF-Connecting-IP` instead. From any other address that header is ignored, so it
  cannot be forged by calling the origin directly. The ranges are built in (`tools.CLOUDFLARE_RANGES`,
  fetched 2026-11-19). Before this, a Cloudflare-proxied Odoo with `proxy_mode` but no nginx `real_ip`
  config saw a Cloudflare edge address and refused Salvor with `403 ip_forbidden`.
- **`ip_forbidden` says what Odoo saw:** the 403 body now carries `remote_addr` (the address checked)
  and `cloudflare` (whether it is a Cloudflare edge). Only a caller holding the database's token gets
  that far; the allowlist itself is never returned.
- **Pairing errors are readable:** a refused pairing shows Salvor's own explanation (its `detail`), e.g.
  the https-only message, not just the HTTP status.
- **Pairing proves reachability:** right after pairing, the module asks Salvor to call
  `/salvor/v1/info` with the new token. If Salvor cannot get through (wrong address seen, TLS,
  firewall) the settings form says so at once (Connection test), instead of the first backup failing.
  The pairing itself is kept either way. A Salvor without the check answers 404: "Not tested".

# Salvor Connector 2.0.13

**Use 2.0.13. Do not use 2.0.12:** it trusted Cloudflare's `CF-Connecting-IP` header by default on every
install, and after a successful pairing it showed a false error. 2.0.13 replaces it on every branch
(`16.0` to `20.0`).

## Read this first if your Odoo is behind Cloudflare
The module does not read Cloudflare's header on its own (2.0.12 did). Until you switch on
**Odoo is behind Cloudflare** (Settings → Salvor Connector → Settings), Odoo sees Cloudflare's address
and refuses Salvor with `403 ip_forbidden`, unless your own proxy already restores visitor addresses.
Switch it on, then choose Test connection in Salvor, or run a backup from Salvor. Through a Cloudflare
Tunnel the switch has no effect.

## What changed, and why

### The Cloudflare header is an option, off by default
- **What 2.0.12 did.** When a request reached Odoo from an address in Cloudflare's published ranges, the
  IP allowlist checked the `CF-Connecting-IP` header in place of that address. This was on for every
  install, including those that are not behind Cloudflare.
- **Why that was wrong.** Cloudflare's ranges carry the traffic of every Cloudflare customer. A request
  from those ranges is not known to have come through your own zone, so its `CF-Connecting-IP` header is
  not known to be the caller's address. Cloudflare's
  [HTTP headers reference](https://developers.cloudflare.com/fundamentals/reference/http-headers/) says of one
  such case: "For Worker subrequests destined for a non-Cloudflare customer zone, the Worker script
  controls the client IP headers: both CF-Connecting-IP and x-real-ip can be altered by the Worker." The
  caller still needed the database's access token, which every route checks first; what was weakened is
  the allowlist, the second check. 2.0.11 and earlier never read the header.
- **What 2.0.13 does.** The header is read only when an administrator has switched on **Odoo is behind
  Cloudflare** on the module's settings form. It is off on a new install and stays off on an upgrade
  from 2.0.12. With it on, the header is used when the request reaches Odoo from a Cloudflare address
  (the connecting address, or with `proxy_mode` the last `X-Forwarded-For` entry) and holds one valid
  address; it is ignored from any other address, and on a request that carries a `CF-Worker` header,
  which Cloudflare adds to requests made by Workers. If a Worker of your own zone sits in front of Odoo,
  Salvor's calls are therefore refused with the switch on; the Pull Log then says "CF-Worker header
  present".
- **What the switch does not give you.** With it on, the allowlist does not protect against someone
  who already holds the access token. The header arrives from Cloudflare's network, which is not known
  to be your own zone, so a request that did not come through your zone can still carry Salvor's
  address in it, with or without a Worker. The `CF-Worker` rule narrows one path and does not change that. Restoring visitor addresses at your own
  proxy lets Salvor through with the switch off, but relies on the same header and is open to the same.
  What stops it is letting only your own zone reach Odoo: zone-level or per-hostname Authenticated Origin
  Pulls with your own certificate. The access token is the protection.
- **Pairing offers the switch.** If the connection test at pairing is refused because Salvor's request
  reached Odoo from a Cloudflare address while the switch is off, the settings form says so and shows a
  button, "My Odoo is behind Cloudflare: switch it on", with one sentence on what that means. The offer
  is made only when Salvor itself reports that refusal, and the address is taken from a Pull Log row
  written after the new token was stored when there is one, otherwise from Salvor's answer. The module
  never switches it on by itself.
- **`ip_forbidden` says more.** The 403 body keeps `remote_addr`, `cloudflare` and `via_cloudflare` and
  adds `cloudflare_mode` (true when the switch is on), so Salvor can tell the administrator what to
  change. Only a caller that presented the database's access token receives this body; the allowlist
  itself is never returned. Why a Cloudflare address was refused (switch off, `CF-Worker` present, no
  header, or a header that is not one address) is written to the Pull Log only.
- **Cloudflare's ranges.** The built-in list is Cloudflare's published list on 2026-11-20. Nothing is
  fetched at run time. The system parameter `salvor_connector.cloudflare_ranges` (comma-separated CIDRs)
  replaces the list (at most 256 entries); an entry that is not a valid network, is broader than /8
  (IPv4) or /16 (IPv6), is a loopback, private or link-local range, or is an IPv4-mapped IPv6 range
  makes the module ignore the parameter, use the built-in list and log a warning. The parameter is
  parsed once per value, and only for a request that presented the right token.
- **Not for Cloudflare Tunnel.** The switch applies where Cloudflare's own addresses connect to your
  server or proxy. Through a Tunnel the request reaches Odoo from `cloudflared`, a local address, and
  the switch has no effect.

### Pairing and the connection test
- **False error after a successful pairing.** With 2.0.12, every pairing that Salvor could reach ended
  with "The pairing code must look like SLV-XXXX-XXXX." The pairing was saved; the result of the test
  was not. Cause: Salvor's test call updated the settings record ("last call") while the button was
  about to write the test result to the same record; the database refused the second write and Odoo
  ran the button again, by then without a code.
- **A rotation could leave Odoo with the old token.** If a call from Salvor arrived while the module
  was waiting for Salvor's answer to *Rotate token*, the same conflict made Odoo redeem the code a
  second time. Salvor refused it ("Invalid or expired pairing code") and kept the new token, Odoo kept
  the old one, and backups failed until the database was paired again. This was already so before
  2.0.12.
- **The fix for both.** A call from Salvor no longer writes the settings record: it only adds a row to
  the Pull Log, and *Last call* on the form is read from that log (the row of the latest successful call
  is therefore kept past the 90 days until a newer one exists). The new access token and the test
  result are each saved in a short transaction of their own; if the database reports a conflict, only
  that write is repeated, never the request to Salvor. The pairing code is cleared in the same write as
  the token.
- **A test that timed out is not a failure.** When Odoo does not answer Salvor's test in time, the form
  shows "Test timed out", not "Not reachable". An Odoo with a single worker cannot answer the test while
  it is still serving the *Connect* click, so a timeout says nothing about the connection.
- **One notice at a time.** The green "Connected to Salvor" notice and the red "could not reach" notice
  no longer show together. The red notice clears when Salvor next reaches the database; there is no
  need to pair again.
- **A call refused later shows too.** If the latest call that carried the database's access token was
  refused for its address, and no call has got through since, the form shows "Last call refused" with
  the address Odoo saw and what to do, in place of "Connected to Salvor". For a Cloudflare address with
  the switch off it says so and points to the switch; with the switch on it says the call did not come
  straight through Cloudflare's proxy. This is what a database behind Cloudflare shows after the upgrade
  from 2.0.12 until the switch is on. Text that is not an IP address is never repeated on the form (with
  `proxy_mode` the caller can choose what Odoo records); the Pull Log has it.
- **Disabled is shown as disabled.** With *Enabled* unticked the form no longer says "Connected to
  Salvor. Backups of this database can be taken": it says that the Connector is disabled and that Odoo
  refuses every call until *Enabled* is ticked again. (The green notice showed in this case in every
  earlier version.)
- **"Not tested" says how to test.** Every "not tested" result ends with the next step: choose Test
  connection in Salvor, or run a backup from Salvor.
- **Unexpected answers.** An answer to the test request that is not a JSON object is shown as "Not
  tested" (2.0.12 raised an error after the pairing was saved). Entries in Salvor's address list that
  are not addresses are left out of Allowed IPs. An unusable answer to the pairing request itself now
  says what to do: create a new pairing code in Salvor and connect again.
- **Wording.** A pairing that Salvor does not complete is reported as "Salvor did not complete the
  pairing (HTTP …)" with Salvor's reason, in place of "Salvor refused the pairing code": the code is
  often not the problem. When the reason is this database's address, the message names the system
  parameter `web.base.url` and its value.

- README and store page: since 2.0.12 the module opens two connections at pairing, not one (the second
  asks Salvor to test the connection). Both now say so, and say what the second request carries.
- README, "Security": the allowlist is described as it works, with the Cloudflare switch and its limits.
- `SECURITY.md`: latest version, and a section on the 2.0.12 allowlist change.
- `docs/release/2.0.12.md`: marked superseded; two sentences corrected. `TAGS.md`: rows for 2.0.12 and

  2.0.13 form.

### Uninstall and upgrade
- **Uninstall** now also deletes the module's system parameters (`salvor_connector.*`). An override of
  the Cloudflare ranges left behind would have applied again, unnoticed, at the next install.
- **Between the Odoo restart and `-u`** a call for a database that still has the older version is
  answered like a call for an unpaired database (401), where it used to fail with 500. The Odoo log
  says to run the upgrade.

## Not changed
The routes, their body-size limits, the access rights, the protocol and the Pull Log format are as in
2.0.11. Uninstalling the module removes the token hash with the module's tables. The module still opens
connections only to the Salvor URL on its settings form, and only when an administrator clicks
*Connect* or *Rotate token*.

## How it was tested
On real Odoo 16 and 19 servers, outside test mode: pairing, rotation with a concurrent call, the
single-worker timeout, and the upgrade of a database paired with 2.0.12. The Cloudflare rules were run
with real TCP connections from addresses inside Cloudflare's ranges on an isolated test network. They
were not run through Cloudflare's own network.

## Upgrade
Pull your branch, **restart Odoo**, `-u salvor_connector`. Run the upgrade right after the restart: until
it has run, Salvor's calls are refused (HTTP 401, as for an unpaired database), because the new code
needs a setting the database does not have yet. Do not pair again: the pairing is kept, and the calls
work again after the upgrade. An upgrade never switches *Odoo is behind Cloudflare* on: it is off after
the upgrade to 2.0.13, whatever version you come from.
